# Brick 2.1: remembered connections

Flutter is selected; the next bounded improvement is recovery of the user's chosen model connection after restart. The core gains a `CredentialStore` port; the native plugin uses pinned keyring 3.6.3 with explicit platform features. Windows uses Credential Manager, macOS Keychain and Linux Secret Service. The [official crate documentation](https://docs.rs/keyring/3.6.3/keyring/) describes `Entry::new`, password reads/writes/deletion, missing-entry errors and backend feature selection. Linux selects synchronous Secret Service with `crypto-rust`, requiring D-Bus development libraries; there is no default/mock backend in production.

Nonsecret SQLite metadata identifies the saved connection and opaque vault entry. Canonical-directory hashing scopes entry names; endpoint binding inside the vault value rejects a changed endpoint. A missing/locked key disables the restored provider while leaving history available. Retry runs after unlock. Keyless local connections do not access secure storage. The UI never receives the saved key.

Vault and SQLite cannot commit together. Validate first, write a fresh UUID entry, atomically commit preferences/reference, then delete the previous entry. Failed DB writes attempt removal of the new entry. Cleanup failures surface warnings; interruption may leave an orphaned secure entry. Forget deletes the referenced key, clears the provider and then removes metadata, retaining history. This is best-effort coordination, not a distributed transaction or encryption of chat history.

Windows validation uses generated public test values only: an opt-in native-plugin round trip plus four separate Flutter processes, with a fixture that rejects incorrect bearer authorization. Unit tests inject a vault to deterministically exercise locked/missing storage without touching OS settings. The [acceptance record](../ACCEPTANCE.md) distinguishes local verification from unexecuted macOS/Linux CI and OS interaction tests.
