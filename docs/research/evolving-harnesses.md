# Evolving harnesses: DSH and Claude Code Mods

Research date: 2026-10-04. Scope: public primary-source evidence for the Dolores architecture discussion. This note changes no feature, roadmap, acceptance status, or runtime configuration. The Flutter + Rust stack is supplied task context, not a conclusion from a code audit.

## What the examples actually establish

DSH makes the model adapter, tools, session log and agent loop replaceable Cordis plugins. Claude Mods expose in-session JavaScript/TypeScript event middleware, including the ability to replace selected built-in behavior and draw UI. These are concrete precedents for an agent modifying its harness through explicit extension contracts. They do not establish consciousness, autonomous selection pressure, reliable self-improvement, or unrestricted replacement of every running component. The latter are design or research questions, not documented plugin properties. [DSH architecture](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/docs/architecture.md), [Claude Mods launch](https://claude.com/blog/claude-code-mods).

## DSH: composition, introspection, and the real reload boundary

**Documented architecture.** DSH assembles a plugin tree from ordered profile bundles and patches. Services expose interfaces through context keys; required injections express dependencies. Typed events connect plugins, while effect registrations unwind at unload. This explains the architectural rationale: consumers bind to a capability contract rather than one implementation, and replacement need not fork the harness. The architecture explicitly makes loop, prompt assembly, storage, policy and UI extensible. A capability seam distinguishes service definition, provider and consumer. [Architecture](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/docs/architecture.md), [Cordis primer](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/docs/cordis-primer.md).

**Introspection has different depths.** `--dump-config` shows composed startup rows. The `pluginInventory/list` Remote returns a read-only snapshot of module, effective enablement and root Fiber phase (`pending`, `loading`, `active`, `failed`, `unloading`, or no live Fiber). It has neither change subscription, durable failure history nor layer attribution. It registers nothing model-facing itself. The separate `plugin_manager` tool gives agents inventory and management results when mounted; Creator mode enables it, other presets disable it by default. Do not equate an inventory with a model automatically understanding its implementation. [Architecture](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/docs/architecture.md), [Inventory](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/host/plugin-inventory/README.md), [Manager](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/boot/plugin-manager/README.md).

**Hot replacement is conditional.** Base-backed applications enable configuration-only HMR with `root: []`; headless, SDK and ACP disable it, and sdk-minimal omits it. Source-module watching requires explicit roots. Configuration refreshes and module reloads share a coordinated queue; installation runs outside it. Replacement failure removes partial replacements and restores previous modules/implementations. This is not universal application rollback: external effects are not claimed to reverse. Installed package-version replacements require process restart. Framework changes invoke the host's `loader.exit()` hook; HMR does not restart the host itself. Browser code has a separate loading mechanism, and TSX loaders/application Workers are outside the supported package-cache refresh scope. HMR does not rewrite conversation history. [HMR package](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/boot/hmr/README.md).

**Authority and blast radius.** Plugin management changes affect all sessions using the profile and persist. Agent management calls require full access or approval; installed Host code runs in-process outside the workspace sandbox. Dependency build scripts have separate approval. Manifest/lockfile restoration after a failed install cannot undo already permitted build-script effects. The manager protects its own management components, and its activation report describes Host state; browser synchronization failures are separate. These boundaries matter more than the slogan that everything is replaceable. [Manager](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/boot/plugin-manager/README.md).

## Claude Code: Mods are function hooks, not merely plugin refresh

**Launch and availability.** Anthropic announced Mods on 2026-10-01. The current official overview requires Claude Code **2.1.287 or later**, enables Mods by default, and says the early-access `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` variable is ignored. Hooks can run in noninteractive and SDK sessions that load the plugin; custom drawings appear only on supported terminal/Desktop surfaces. The VS Code chat panel has hooks but no mod drawings; Desktop WSL sessions do not load them. [Launch](https://claude.com/blog/claude-code-mods), [Current overview](https://code.claude.com/docs/en/plugins/mods/overview).

**What a mod exposes.** A mod is a normal plugin with `hooks/hooks.json` naming one hooks module. It exports `register(on, options)` and handlers receive `($, e, next)`. Calling `next(e)` delegates; calling it with changed input rewrites; returning directly replaces downstream behavior. Handlers can intercept prompts, tool/permission decisions, streamed requests, commands and UI rendering. A mod can register commands/tools and draw panes, bands and interactive elements. This is deeper than reloading skills or MCP definitions; it adds a programmable interception contract inside the existing engine. The built-in `/diff` is itself replaceable mod behavior. [Public mod source](https://github.com/anthropics/claude-code/blob/1c229fcd1e1e4e452e29a8f116b45fe4cfe2c528/mods/README.md), [Launch](https://claude.com/blog/claude-code-mods).

**Lifecycle is explicit.** Agent-authored mods are written under the session's `~/.claude/dev-mods/<session-id>/` directory. After approval to enable session hot reloading, changes load at the end of the turn. That approval survives resuming the same session. `--plugin-dir` watches a developer-owned directory for reloads; `register` runs again and module variables reset. Session-created folders are eventually cleaned up; copy and install a mod to retain it across sessions. Installed copies are version-cached, so changing development source is not an installed-plugin update. The engine writes build-specific declarations beside development mods, which outrank online docs when they disagree. [Create a mod](https://code.claude.com/docs/en/plugins/mods/create).

**State and interruption.** `$.state` survives module reload, but ends or resets with the session and `/clear`, `/resume`, or `/branch`. `$.store` persists in a plugin-owned JSON store across sessions until deletion or inactivity cleanup. Store read-then-write is not atomic across sessions. `session.start` does not fire for those three state resets; restoring stored values requires the appropriate `classic.SessionStart` event too. Timers stop on module reload. `next.signal` lets a hook stop long-running work when its event is abandoned. None of this promises exactly-once external effects or automatic state-schema migration. [UI/state lifecycle](https://code.claude.com/docs/en/plugins/mods/interface), [Background work and cancellation](https://code.claude.com/docs/en/plugins/mods/api).

**Composition and recovery.** Events form an ordered middleware chain: managed guard/prepended mods, installed mods, managed appended mods, then other built-ins. Installed dependencies influence ordering. A handler that fails before delegation is skipped, so downstream behavior can run; a failure after delegation preserves the completed result without executing it twice. A safety handler must explicitly return denial from its `.catch` path to fail closed. Hot reload alone is therefore insufficient as a safety guarantee. [Event ordering and failure semantics](https://code.claude.com/docs/en/plugins/mods/events).

**Process boundary is not a security sandbox.** Hook modules have no direct Node or DOM APIs; outside operations go through `$`, allowing static inspection. Nevertheless mods can read/write as the host user, start processes outside Bash's sandbox, use the network and spend model usage. The built-in `sec-default` guard protects managed hooks/instructions and deny rules where it loads. Its tool deny rules do not automatically block a mod's own `$.fs` or `$.process` operations; an outer policy mod or refusal to load is needed. It is incorrect to describe the mediated JavaScript environment as OS containment. [Overview](https://code.claude.com/docs/en/plugins/mods/overview), [Organization controls](https://code.claude.com/docs/en/plugins/mods/admin).

## Practical implications for Dolores — design inferences, not implementation instructions

For the supplied Flutter + Rust architecture, adopt the **contract** ideas without assuming Node/Cordis or Claude's API can be loaded into the application unchanged:

| Potential Dolores contract | Why it is useful | Boundary to decide |
| --- | --- | --- |
| Versioned inventory of providers, tools, loop stages, prompts and UI contributions | Gives the agent an accurate description of what it can inspect or change | Separate declarative/runtime facts from private source and credentials |
| Ordered event middleware with documented replace/delegate semantics | Allows narrow behavioral changes without rebuilding every component | Pin ordering; keep non-bypassable policy outside agent-owned middleware |
| Disposable capability registrations | Makes removal predictable and avoids stale tools/listeners | Own tasks, cancellation, resources and cleanup explicitly |
| Candidate validation followed by activation at an idle/turn boundary | Makes generated changes reviewable and contains failures | Define in-flight requests, outstanding tools and rollback behavior |
| Host-owned session state plus durable versioned storage | Preserves usable work while modules reload | Define migrations, concurrency and restart recovery |
| Declarative UI contributions interpreted by Flutter | Allows useful in-session presentation changes | Whitelist components and actions; do not promise arbitrary release-Dart hot swapping |
| Bounded script/Wasm/worker extensions or restartable sidecars | Creates a plausible replaceable execution unit around the Rust host | Select actual process/OS capabilities and resource budgets; a worker alone is not isolation |

These choices would support a bounded loop of observing failures, proposing an extension, checking it, activating it, measuring the outcome, and retaining or reverting it. They would not make improvement automatic. A persistent identity/personality model, permission to pursue long-lived goals, and evaluation of whether a change improves the user experience remain separate product contracts. An agent-generated patch that changes the evaluator or safety gate also changes the meaning of its claimed success; keep that authority explicit.

## Evidence limits and unresolved facts

- This was documentation research; no DSH or Claude runtime was executed, no model reliability claim was tested, and Dolores code was not audited. Installed versions and enterprise settings can differ from public documentation.
- DSH source was observed at `5badb15009ae1756c3afe0ae0cef1faafc290ccc` (commit timestamp 2026-10-03T03:48:13Z), with root manifest version `0.2.1-alpha.1`. This identifies the researched tree, not every package's version or the user's installed runtime. The README still labels DSH a developer preview with breaking changes. [Commit](https://github.com/deepseek-ai/deepseek-harness/commit/5badb15009ae1756c3afe0ae0cef1faafc290ccc), [Root manifest](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/package.json), [README](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/README.md).
- Claude repository source was observed at `1c229fcd1e1e4e452e29a8f116b45fe4cfe2c528` (2026-10-02T20:19:38Z), but its published declarations identify **2.1.277 early access**. Its README still describes an enablement gate. These are older API evidence, not grounds to contradict the launch-era 2.1.287+ official docs. Regenerate types from the actual running build. [Public declarations](https://github.com/anthropics/claude-code/blob/1c229fcd1e1e4e452e29a8f116b45fe4cfe2c528/mods/types/claude-code.d.ts), [Public README](https://github.com/anthropics/claude-code/blob/1c229fcd1e1e4e452e29a8f116b45fe4cfe2c528/mods/README.md).
- Neither example establishes safe arbitrary mid-stream replacement of the whole native host, complete reversal of external effects, or a verified rollback for every candidate. Those would need separate lifecycle specifications and realistic recovery tests.
- No official source examined establishes consciousness, general autonomous self-evolution, automatic long-term improvement, or portable compatibility between DSH plugins, Claude Mods and Dolores. Treat these as aspirations or hypotheses until independently specified and evaluated.
