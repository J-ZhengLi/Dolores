# Flutter bridge contract

## Reviewed creation and removal (brick 3.7)

Working chats additionally advertise `create_text_file {path:string,content:string}`. Both fields are required, extra fields rejected, serialized arguments at most 4096 UTF-8 bytes. It creates one direct relative UTF-8 file in an existing directory, never overwrites a file/directory/alias, uses the existing secret/VCS/device/traversal policy and accepts empty content. File and full addition diff each have a 16384-byte cap. The complete literal diff binds the existing run/call approval; Create once/Deny replaces the edit action label. Successful ToolRecord status is `created`; content is JSON `{applied:true,created:true,bytesBefore:0,bytesAfter,changeId,journalStatus:applied|pending}` in the selected journaled host. Diff is optional on legacy records; creation requires it at approval. No model permission field is added.

Schema 8 adds `beforeExists:boolean,afterExists:boolean` to FileChange summaries. Schema-7 records migrate with both true and unchanged snapshots. Empty bytes with true mean an existing empty file; false means absence. `changeDetails` derives `/dev/null` headers from those flags. `previewRevert` additionally returns `operation:"restore"|"remove"`. Original pending/applied replacements restore text; original creations with matching current bytes prepare removal. Invalid/reverse records are refused. Apply retains one-use scope/expiry rules; removal results add `removed:true` to `{applied:true,bytesBefore,bytesAfter,changeId,journalStatus}`. Cancel and inspection never write or call a model.

Creation exclusively stages and flushes before intent, then publishes by a no-overwrite hard link; unsupported filesystems fail without rename fallback. Removal rechecks bytes/direct path/ordinary permissions before and after its reverse intent, then removes one recorded file. Removed-file receipts remain honest on failure; reverse-of-reverse is unavailable. Applied effects survive later chat failures and records survive chat deletion. See [creation boundaries](../design/approved-creation.md); older schema/tool descriptions below are historical.

## Reviewed file edits (brick 3.5)

Working chats now advertise four tools, adding `edit_text_file {path,old_text,new_text}`. Preparation reads a bounded local snapshot for one exact unique replacement, producing `ToolRequest.diff`; Apply once must match the current run/call/preview. No write occurs on preparation, Deny or Stop before publication. Direct existing writable UTF-8 files only; file/diff limits are 16 KiB, arguments 4 KiB. Scope is the saved immutable folder. Bytes and ordinary permissions are rechecked before staged atomic replacement; a changed file returns a fixed conflict without overwriting. Checks are optimistic against concurrent external writers.

`ToolRecord.diff` is optional and successful edits use `status:edited` with JSON `{applied:true,bytesBefore,bytesAfter}`. Chat/trajectory and full exports retain the local diff with successful history; old records/schema 6 remain valid. Denials include `(name,target,query,diff)`. Applied file changes remain even if later Stop/model/save fails; failed-run cards are transient, not a durable journal. No new command or approval field granting permission is added. See [design](../design/approved-edits.md). Historical three-tool/read-only descriptions below are superseded.

## Streaming agent progress (brick 3.4)

Working chats use streamed function calls. `modelStep` starts a call, followed by `{type:modelText,id,number,text}` deltas for public text. Flutter replaces active text at the next step, retaining earlier commentary as transient progress. Events expose no partial arguments and cannot approve tools. Valid completed calls still produce `toolApproval` then `toolResult`. Final text arrives through `modelText` without duplicate `delta`; side chats retain `delta`. `done` follows complete-pair persistence. Run and step IDs exclude stale text.

Successful metadata adds optional `agent.steps:[{number,text}]` for up to three intermediate calls; final text remains assistant message content. Old summaries remain readable. Chat/trajectory and both exports preserve progress; schema 6 is unchanged. Failure discards incomplete current text and restores the draft; earlier transient commentary is labeled Not saved. The 128-KiB text budget covers all agent calls. See [design](../design/streaming-agent.md). This supersedes brick 3.1's nonstreaming transport/per-call text budget.

## Working sessions (brick 3.3)

The selected shell defaults sidebar New chat to a temporary working folder. Each project has a + action to start a new chat in that folder. Explicit Side mode retains streaming without tools. `createSession` validates project folders, creates distinct temporary folders under the application data directory, or creates a side session with a null root. Temporary/side reject a supplied path. Creation and workspace reads are excluded during active generation. Project creation also updates the bounded 50-entry recent-project list. Session pages and bootstrap rows add local workspace identity; the raw shared Session type used in exports and alternative shells is unchanged.

Schema 6 adds `projects(root,name,updated_at)` and `session_workspaces(session_id,kind,root)`, preserving previous messages and metadata. Session creation/binding/project registration is atomic. Old sessions restore Side mode. The folder is immutable for the chat, restored after restart, and opened again before each run; unavailable folders fail instead of disabling tools. An optional legacy Start workspace must resolve to the same bound root and cannot enable file access for an existing side session. Working chats advertise all three tools even for ordinary prompts. The default temporary folder is created lazily on first send; startup and context preview remain nonmutating.

These absolute paths are private local host state, not automatic model context or exports. Folder contents still reach the selected provider only through approved tool results. Temporary means app-managed workspace, not an unsaved or expiring history. Deleting a chat cascades its binding, preserves project recents, and never deletes working-folder contents. This supersedes brick 3.1's launch-only folder toggle. Per-operation approval and run/resource limits remain unchanged.

## History pagination and complete export (brick 2.2)

Bootstrap's `sessions` and additive `sessionPage` expose the same first 50 entries. `sessionsPage` returns `{items,hasOlder,hasNewer}` using a cursor `{updatedAt,id}` from the first or last displayed row. Order is `updatedAt DESC, id ASC`, including deterministic timestamp ties. Older is the default; newer requires a cursor and returns the preceding page in the same display order. Boundaries are exclusive. A deleted boundary still works. Session updates can reorder entries: this is live browsing, not a multi-request snapshot; refresh returns the newest page.

`messagesPage` returns chronological `{id,role,content}` entries, up to 80. With no cursor it loads the latest page. A positive message ID selects older (`id < cursor`) or newer (`id > cursor`) rows; newer requires a cursor. Missing sessions return `Conversation no longer exists.` UI pages replace each other and expose both direction flags, while `messages` retains its legacy bounded context behavior. No messages are deleted by paging. The default SQLite plugin supports page limits 1–100 sessions / 1–80 messages internally; the Flutter commands always use 50 / 80. Queries use a consistent read transaction for items and direction flags. The session ordering index is additive; the schema remains version 3.

`export` writes the whole saved conversation, independent of the displayed page or provider context. Formats are `markdown` and `json`; the absolute destination must end in `.md` or `.json` respectively (case-insensitive). The destination must not exist. Export streams rows from a consistent SQLite read transaction through a buffered writer into a temporary file in the selected folder, syncs it, then publishes without replacing an existing file. Failed writes drop the temporary file and leave no partial destination. A crash may leave an unreferenced temporary file; directory durability and no-clobber publication atomicity are platform/filesystem dependent. A raced/existing destination is never overwritten. Folder/permission/I/O errors are user-facing and exclude secrets.

JSON shape: `{exportVersion:1,session:{id,title,updatedAt},messages:[{id,role,content,metadata?}]}`. `updatedAt` is Unix milliseconds; messages are chronological. This is an export format, not an implemented import API. It contains no connection metadata or credentials. Markdown uses role headings with literal text fences sized to preserve embedded backticks, including the title. Saved conversations may themselves contain sensitive text; the user chooses their output file. All history/export commands share the generation exclusion rule. Canceling the native Save dialog sends no export command. UI view state keeps only the 20 most recently visited drafts/scroll positions in process memory, not across restart.

The selected Flutter shell loads the bundled Rust library in the same process with `dart:ffi`. There is no HTTP server, Node sidecar, or third-party plugin ABI. All calls run in one Dart worker isolate. SQLite and secure storage stay off the UI isolate; Rust runs generation on two Tokio workers with at most two blocking workers.

## C ABI v1 and memory ownership

`dolores_call(const uint8_t *input, size_t length) -> char *` accepts UTF-8 JSON, at most 128 KiB. A null pointer, oversized input or invalid request returns an error envelope. The caller must keep the input allocation readable for the call; this trusted in-process ABI cannot validate arbitrary pointers. The result is owned, NUL-terminated UTF-8 JSON: `{ "ok": true, "result": ... }` or `{ "ok": false, "error": "..." }`. No Rust panic intentionally crosses the C ABI.

`dolores_free(char *result)` frees a result **exactly once**, in the same library that allocated it. Null is allowed. Dart frees its own request allocation separately. Never pass another allocation or an already-freed pointer.

The engine initializes once per process, on the first valid command. It uses an absolute `DOLORES_DATA_DIR` override or the shared `dev.dolores.desktop` application-data directory and `dolores.db`. Initialization attempts remembered-connection recovery. Failure produces a warning rather than blocking history. `shutdown` cancels/releases the active run; it does not destroy the process-wide store/runtime, forget saved credentials, or clear configuration.

## Approved folder tools (brick 3.1)

Folder tools is a native folder-selection action in the sidebar. Canceling it preserves the previous selection and sends no command. The absolute folder stays in Flutter memory for this launch; `start.workspace` opens a native directory capability. No path is retained in connection preferences, bootstrap, successful turn metadata or exports, or sent to the provider. Tools are disabled without a folder. The compiled plugin is trusted native code, not an external plugin sandbox.

The only advertised function is `read_text_file` with arguments `{path:string}` and no additional fields. It accepts relative forward-slash paths of at most 1024 UTF-8 bytes. It rejects traversal/absolute/control-character paths, Windows device names, common credential/VCS names (`.git`, `.ssh`, `.aws`, `.env`/`.env.*`, `dolores.db`, `id_rsa`, `id_ed25519`), and outside-directory symlink/junction resolution. Names are revalidated after resolution and before reading. Only regular UTF-8 files up to 16384 bytes without NULs are read. The name filter does not detect every possible secret; the user must inspect the target before allowing it. File contents may change between approval and reading.

Additional ordered run events are `{type:modelStep,id,number}`, `{type:toolApproval,id,request:{callId,name,target}}`, and `{type:toolResult,id,record:{callId,name,target,status,content}}`. Targets are resolved relative names, not absolute folder paths. Status is `read`, `denied`, `blocked` or `error`; denied/blocked/error content uses fixed local messages. Each valid read waits for Allow once or Deny. A denial suppresses repeated prompts for that target within the run, without granting access. A decision must match both the current run and pending call; Stop, timeout and shutdown discard pending approvals. Model arguments, file text and provider error bodies cannot authorize access. While waiting, polling slows to 200 ms; no polling runs when idle.

Tool mode uses non-streaming Chat Completions function calls and a maximum of four model calls/four tool calls. Arguments are limited to 4096 bytes, JSON responses to 262144 bytes, individual result text to 16384 bytes, serialized message context and each model text to 131072 bytes. The initial context appends local guidance to the existing system message and trims complete old pairs if necessary. Its preview/started/saved context summary describes the initial request before file results. Later call contexts include bounded results and are checked independently; the ring is not a cumulative model token window. `max_tokens` applies to each call. Each response has the configured provider deadline; the host additionally bounds the entire model/tool/approval phase to `min(timeoutSeconds,300)` seconds. Initial folder opening/history preparation and final atomic persistence are outside this phase. Filesystem tasks use the two-worker blocking pool; cancellation stops waiting, but cannot forcibly interrupt an OS filesystem operation already running.

Only the final answer is emitted as `delta` and saved. Successful metadata adds `agent:{modelCalls,usageByCall:[TokenUsage|null],tools:[ToolRecord]}`. Its top-level `usage` is null; no sum or price is inferred. Approved file contents are shared with the selected provider and retained unencrypted in the successful reply's metadata and full JSON/Markdown exports. Schema 5 already stores extensible metadata; legacy records omit `agent`. Final text, metadata and user message commit together. Stop, failure and loop exhaustion never save partial pairs; their transient result cards remain visible until the next run/view, with no durable failed-run audit claim. Saved cards are expandable in both chat and trajectory.

Unsupported/malformed tools, reused call IDs, incomplete responses, context exhaustion and loop exhaustion fail with local guidance without retry/fallback. Disable folder tools to return to ordinary streamed chat. There are no write, shell, listing/search, remembered approval, pricing limits or external tool-loader capabilities in this brick. Iced/Tauri retain plain chat.

## Folder listing and text search (brick 3.2)

The explicit folder registry now contains `read_text_file`, `list_folder` and `search_text`, sharing one directory capability. Function-call wire ordering, run exclusion, single-use decisions, four model/four tool budgets, final-answer emission and whole-phase timeout are unchanged. Each listing/search waits for approval before enumerating names or scanning file contents. Search approval allows the bounded scan and matching snippets; it never grants a subsequent full-file read. Root scope is exactly `.`; other scopes are direct relative forward-slash folders. Results always report paths relative to the chosen root, including a scoped subfolder prefix, so a later read can use the same path.

`list_folder {path:string}` has no additional fields or query. It inspects at most 512 entries in one folder level, returns at most 100 sorted entries from that bounded inspected subset, and caps serialized output at 16384 bytes. Its result string is JSON `{entries:[{path,kind:file|folder}],inspectedEntries,skippedEntries,truncated}`. If the enumeration/result cap is reached, `truncated:true` indicates partial coverage. The sorted subset is not guaranteed to contain the globally first names in an oversized folder. Excluded/unavailable names are not disclosed in the skipped count.

`search_text {path:string,query:string}` accepts a nonblank, case-sensitive literal single-line query of at most 256 UTF-8 bytes, without control characters. It does not interpret regex, shell syntax or glob patterns. The query is copied into the approval request and successful/denied record. It visits up to four subfolder levels, inspects at most 256 entries, attempts at most 64 file reads, and reads at most 262144 bytes in total. Regular UTF-8 text files up to 16384 bytes without NULs are eligible. Large, binary, unreadable and invalid-UTF-8 files are skipped; incomplete reads at the byte boundary are not searched. Results are JSON `{matches:[{path,line,text}],inspectedEntries,attemptedFiles,scannedFiles,skippedFiles,skippedEntries,bytesRead,truncated}`. Lines are one-based; up to 30 matching lines have at most 240 Unicode characters of snippet, within a 16384-byte serialized result cap. `scannedFiles` counts successfully decoded searched files, not failed attempts. Budget/depth/output limits set `truncated:true`; no matches does not imply absence in excluded or omitted files. Files can change while scanning; this is not a filesystem snapshot.

Both discovery tools skip symlink/junction entries, reject alias scopes, preserve the common credential/VCS path filter, and exclude `node_modules`, `target`, `build`, `dist`, `.dart_tool`, `.venv`, `venv` and `__pycache__`. Counts may include filtered entries but never their names or contents. The filename filter cannot detect all sensitive content. Capability-relative resolution/open and cancellation checks stay on the bounded blocking pool, without indexing or idle work. An OS call already running cannot be forcibly interrupted.

`ToolRequest` and `ToolRecord` add optional `query:string` only for searches; legacy records deserialize without it. Record status is `completed` for a successful listing/search, `read` for a successful file read, and `denied`, `blocked` or `error` otherwise. Denials now match `(name,target,query)` within a run, so denying a listing does not silently deny a search or read, and a different query requires a new decision. Query/path/model disclosure uses literal selectable text. UI cards turn known listing/search JSON into names or file/line/snippet text with skipped/partial labels; unknown/legacy payloads remain literal. Names, queries and snippets are sent to the configured endpoint and saved unencrypted/exported only with a completed turn; the absolute root and approval are still launch-only. Schema stays 5; saved trajectory uses the same records.

## Remembering and recovery

An explicit string replaces the key; `""` selects a keyless connection. Null/omitted `apiKey` reuses an active or saved key only for the exact same base URL. If none exists it selects an empty key; it never retrieves a key from another endpoint. `configured` means locally configured, not network-tested. `rememberConnection` means metadata exists; `hasSavedKey` means this process successfully saved/restored a secure key. The key and opaque credential ID are never included in responses.

With remembering enabled, SQLite schema version 4 holds nonsecret preferences, model choices and an opaque UUID. Migration adds missing model-choice and turn-metadata tables without discarding earlier metadata/history. The credentials plugin uses explicit keyring 3.6.3 native backends: Windows Credential Manager, macOS Keychain, Linux Secret Service. Credential names include a hash of the canonical data directory; copying a DB to a different directory does not reuse its key. Key material includes an endpoint binding inside secure storage. Keyless local connections can be remembered without accessing secure storage. There is no plaintext or mock-backend fallback. If secure storage is locked/unavailable, unlock and retry, re-enter the key, or choose a connection for this launch only.

SQLite atomically updates preferences and their reference. Vault and SQLite cannot share a transaction: a new key is written first, failed metadata writes attempt deletion, and a successful replacement attempts deletion of the previous key. A crash or failed cleanup can leave an unreferenced secure entry; cleanup failure is reported without exposing the secret. Forget deletes the saved key before clearing metadata; a locked vault rejects forgetting, while a later metadata failure leaves the active connection cleared and reports the failure. These operations are serialized in the worker. History is not encrypted by this feature. Changes made by another shell invalidate restoration when preferences differ.

## Model discovery and selection

listModels sends GET <baseUrl>/models using validated draft settings and an explicit or same-endpoint active/saved key. It does not save settings or require a model name. Unavailable, unsupported, malformed or empty listings return sanitized errors; manual IDs remain supported. The request is bounded to 20 seconds, 1 MiB and 512 rows. IDs are nonblank, at most 200 UTF-8 bytes, with no control characters; duplicates are removed and results sorted. Listing does not guarantee text-chat capability for every model.

enabledModels accepts 1–32 IDs, including the active model. Choices are saved atomically with preferences/reference, even for launch-only connections. selectModel requires a configured provider and an enabled ID. It reuses the provider client/key and updates preferences/remembered metadata together, without rotating the vault entry or changing history/draft. Old records without choices expose their active model. Connection changes replace choices for the endpoint. Both commands are excluded during generation; there is no idle fetching.

## Events and completion

- `{type: "started", id, session, context}` after session/history preparation.
- `{type: "delta", id, text}` for streamed Unicode text.
- `{type: "done", id, answer}` after a successful atomic complete-turn transaction, or `{type: "done", id, error}` on failure/cancellation.

The event queue and text channels are bounded to 32 entries. Dart drains only while a run is active, scheduling the next poll 25 ms after the previous one resolves; there is no idle polling. Cancellation interrupts a producer blocked on forwarding. Deltas are drained before completion. A late Stop after the atomic transaction starts loses to successful completion. Failures restore the unsaved draft; partial turns never become durable history.

The core's 16 KiB input, 128 KiB context/output and 40-turn history limits still apply. Provider URL/model/key validation and sanitized errors are shared with the other shells. Native pointer/IME interaction, accessibility and macOS/Linux packaging are separate acceptance checks.

## Usage and context visibility

Brick 2.3.2 adds `context {session?:string|null,input:string}`. An empty draft is allowed; oversized input, a missing session or corrupt history returns a sanitized error. The command reads the latest bounded saved history and its total count from one SQLite snapshot, regardless of the viewed page. It creates no session, changes no draft/history/settings, and makes no network request. It shares generation exclusion. Flutter invokes it only on demand and excludes concurrent actions while it runs.

`ContextSummary` is `{includedTurns,savedTurns:u64|null,omittedTurns:u64|null,textBytes,maxTextBytes,maxTurns}`. Saved and omitted counts are unavailable for plugins lacking a total-count capability. Text bytes are exact UTF-8 content bytes of the selected messages, including the system instruction and current draft; JSON envelopes and role names are excluded. The existing 40-complete-turn/131072-byte limits remain unchanged and can exclude older turns even on the newest page. Older turns remain saved. These app bounds neither estimate tokens nor guarantee a particular model context window. `started` adds the actual request's `context`.

The `context` result now adds `messages:[{role:system|user|assistant,content:string}]` alongside those summary fields. These are the same prepared messages in request order, at most 82 entries and 131072 content bytes, from the same read snapshot. Empty draft remains an empty final user message. No credentials, endpoint, HTTP headers or request envelope are included. This preview is not saved in SQLite or added to started events/turn metadata. The UI groups the actual messages into system/history/draft and computes the composition from UTF-8 bytes.

The chat trajectory uses the existing `messagesPage` command with its own cursor and page, leaving the main transcript/draft/scroll unchanged. Reads are excluded during generation. During generation the inspector starts from the displayed page and exposes live lifecycle events; after completion it refreshes latest history if the inspector was already viewing latest. The Flutter-only Log retains at most 200 events across conversations in process memory, with local observation time, request ID, original model, monotonic elapsed time and lifecycle label. It coalesces streaming into one first-text event, moves new-chat events to the assigned session, and removes that session's events when deleted. Stop/failure labels are observations, not persisted audit records; successful history survives restart while this log does not. No new trajectory API, per-chunk trace, raw errors or network logging is introduced.

Completed assistant items in `messagesPage` and exports may include `metadata:{model,usage:TokenUsage|null,context:ContextSummary}`; legacy items omit it. `TokenUsage` contains nullable `inputTokens,outputTokens,totalTokens,cachedInputTokens,reasoningTokens`. Counters come only from the provider: zero stays zero; missing/invalid counters stay null; totals are not calculated. Cached and reasoning counters are breakdowns, never added to totals. No costs, tokenizer, aggregate session totals or metadata for unsuccessful requests are claimed. The saved model identifies the completed request even after model switching.

Schema version 4 adds an optional `turn_metadata` table with cascading message ownership. Existing schema/history/credentials are preserved. A complete user/assistant pair and the assistant's metadata are written in one transaction; failure rolls all back. JSON export version 1 gains optional message metadata; Markdown export uses a separate inert text-fenced record after that reply. The older `messages` command remains text-only. Optional provider/storage methods default to unavailable accounting/no metadata persistence, preserving existing plugin implementations and alternative hosts.

The provider requests `stream_options:{include_usage:true}` and accepts usage on an empty-choices final chunk, as described in the [official streaming contract](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create). Null usage chunks do not replace a valid snapshot; repeated snapshots replace rather than accumulate. Only nonnegative integral JSON counters up to 9007199254740991 are retained. A bounded, explicit HTTP 400/422 unsupported-parameter rejection may trigger one attempt without the option before streaming starts. No generic validation/denial/transport/mid-stream retry occurs and error bodies remain hidden. Interrupted streams may lack usage; errors/Stop still discard the unsaved pair.

## Request controls and recovery (brick 2.4)

`bootstrap` additionally returns `requestSettings:{maxOutputTokens,timeoutSeconds}`. `setRequestSettings {settings:{maxOutputTokens,timeoutSeconds}}` returns null on success. Both fields are required JSON integers: maxOutputTokens 1–32768 (default 2048), timeoutSeconds 1–900 (default 180); unknown settings fields, fractions, negatives and out-of-range values are rejected. Saving is excluded during generation and makes no network request. SQLite schema 5 stores one nonsecret settings record; save/restart, model switching, connection recovery and Forget preserve it. Validation/storage failure preserves the prior provider/settings. Provider construction is validated before storage; activation follows a successful save. Optional core storage/provider methods preserve other plugin implementations; unsupported stores can reject saving.

The OpenAI-compatible provider sends `max_tokens: maxOutputTokens` using the existing text chat-completions format. Individual models can reject this parameter or lower their output ceiling; the app's 128-KiB output and context bounds remain. A single cooperative deadline covers provider execution from its start through headers, streamed body and output-channel waits, including both attempts when the bounded unsupported-usage-option fallback applies. It does not include local context reads or final SQLite persistence. The fixed 10-second connect timeout and 20-second discovery timeout remain. Cancellation wins promptly. Timeout discards the incomplete turn and restores the unsent draft.

Started events are now `{type:started,id,session,context,requestSettings:RequestSettings|null}`: the actual provider's snapshot, null for plugins that do not report it. Completed assistant metadata optionally adds `requestSettings`; old messages/plugins omit it. It commits atomically with text and remains unchanged when settings change later. JSON and Markdown exports retain it.

Failure terminal events are `{type:done,id,error,recovery:{kind,retryable,guidance}}`. Known first-party adapter errors produce kinds stopped, timeout, network, rateLimit, access, configuration, outputLimit, storage or provider; unknown plugin errors use unknown with retryable false. Guidance is fixed local text, never raw provider bodies. retryable indicates an offered manual Retry message action, not an automatic retry or a guarantee of success. Stop offers no failure retry; access/configuration errors direct users to Model connection; timeout/output limits offer Request settings. Rate-limit/server failures ask users to wait. Storage failures ask users to review Trajectory before sending again. Error handling never sends a new request automatically; the existing unsupported-usage-option compatibility attempt is unchanged.

The settings dialog preserves the draft, validates whole numbers, and resets defaults locally until Save is clicked. Saving locks dismissal to prevent duplicate/pending actions; failed saves remain editable. After a failed request, Retry message sends the current editable draft, including any user corrections, through the normal generation guard. Editing settings leaves failure guidance available; an unrelated later error hides stale guidance. No partial failed/stopped reply is persisted. Reply details display saved output limit/timeout when known and leave legacy settings unavailable.


## Change journal and reviewed revert (brick 3.6)

The selected Flutter host now registers journaled file tools. Core storage and journal ports remain optional; an unsupported storage plugin prevents publishing an edit when intent cannot be saved. SQLite schema 7 adds independent folder-bound file-change rows and FULL synchronous write-ahead intent, preserving schema-6 history, credentials, workspaces and metadata. Existing edits are not backfilled. Snapshots/root are unencrypted local data, excluded from automatic context and conversation exports. Each file snapshot is limited to 16 KiB; disk retention grows with edits and chat deletion never purges it.

| Command | Arguments | Result |
| --- | --- | --- |
| `changesPage` | `session:string,cursor:i64|null` (optional) | `{items:FileChange[0..20],hasOlder,hasNewer}`; descending ID, older cursor excluded; `hasNewer` indicates an older page, UI uses Newest |
| `changeDetails` | `session:string,changeId:i64` | `{change:FileChange,diff:string}`; local literal forward diff, no raw snapshots/root |
| `previewRevert` | `session:string,changeId:i64` | `{token:string,target:string,diff:string}`; current bytes must match after snapshot, original pending/applied edits only; no mutation |
| `applyRevert` | `session:string,token:string` | `{applied:true,bytesBefore,bytesAfter,changeId,journalStatus:applied|pending}`; one-use approval, fresh checks and write-ahead reverse receipt |
| `cancelRevert` | `token:string` | null; clears matching pending plan without modifying the file |

All five are excluded during generation. Folder identity comes from the saved session; mismatched folders, Side/missing chats and unavailable files are refused. One opaque preview is bound to session/root/change ID and expires after five minutes, checked on Apply. New preview, Cancel, Delete, Start and Shutdown release it; expired handles are bounded to that single slot until the next release. Repeated/wrong/expired approvals fail, and Apply consumes the plan even on refusal. Reverse diff is limited to 16 KiB. No new model tool, provider request or C symbol is added.

`FileChange` is `{id,createdAt,target,status,reverts:i64|null,bytesBefore,bytesAfter}`. Status is pending/applied/notApplied/reverted; pending means intent was saved but no completion receipt exists. It is displayed as Needs check. `reverts` identifies a separately recorded reverse operation; reverse operations cannot themselves be reverted in this brick. Local details can display a forward diff of at most roughly 2 file snapshots plus line markers; only one detail is loaded.

The tool-edit success payload now adds `changeId:i64,journalStatus:applied|pending` to `{applied:true,bytesBefore,bytesAfter}`. These fields are present on journaled production calls and omitted on unjournaled alternative registrations. Intent failure prevents publication; completion failure after publication still reports applied true and pending. A late chat failure/Stop does not remove the journal. Revert completion atomically marks its row applied and the original reverted; database failure can leave both uncertain while the filesystem effect remains. No automatic reconciliation/rollback occurs. Exact current-text checks guard any later review. See [design and concurrency limits](../design/change-journal.md).
