# Dolores API

Brick 3.3 adds selected-shell `createSession {kind:project|temporary|side,path?}` and `workspace {session}`, persistent per-chat folder identity, and recent `projects` in bootstrap. Main chats include tools automatically; Side mode is explicit. Schema 6 stores workspace associations/project recents privately and preserves legacy messages as side chats. Start follows the bound folder, cannot redirect an existing chat, and creates a temporary working session when no session is provided. Context inspection derives guidance from saved identity without creating folders. Absolute roots are excluded from automatic provider context and exports; deleting a conversation never deletes working files. This supersedes the historical launch-only behavior below. See [working sessions](design/working-sessions.md).

The selected Flutter shell uses an in-process Rust C ABI; there is no HTTP server or sidecar. Iced uses internal Rust events/tasks and Tauri exposes local IPC as optional comparison shells. All assemble the same provider/storage plugins and make the same outbound requests. No arbitrary shell API is exposed. Flutter supports explicit conversation export to a chosen new file. Errors exclude raw provider bodies, authorization headers and endpoint credentials.

See [the desktop contract](desktop/desktop-api.md) and [the machine-readable contract](openapi.json). The OpenAPI file has an empty `paths` object because there are no HTTP endpoints; `x-tauri-commands` describes the actual IPC surface.

See [the Flutter bridge contract](flutter/flutter-api.md); `x-flutter-ffi` in the machine-readable contract describes commands, events and ownership. Brick 2.1 adds an OS credential plugin, optional `rememberConnection` on `configure`, nullable/omitted `apiKey` to reuse a saved key for the same endpoint, `recoverConnection`, and `forgetConnection`. Bootstrap adds nonsecret `rememberConnection`, `hasSavedKey` and `connectionWarning` fields. Keys are never returned; locked/missing secure storage leaves history available. Iced/Tauri retain their existing memory-only connection behavior.

Tauri generation sends an empty delta to acknowledge run reservation before text deltas. This forwards Stop during preparation; invocation completion determines persistence. Iced reserves its run synchronously before scheduling work, uses a cancellation token and internal run-numbered events, drains the bounded stream, then atomically commits a successful complete turn. Once a commit starts, completion wins over a late Stop. Internal events are not a public API.

Outgoing plain-chat contract: `POST <baseUrl>/chat/completions`, optional `Authorization: Bearer <apiKey>`, JSON `{model, messages: [{role, content}], stream: true, max_tokens: maxOutputTokens (default 2048), stream_options: {include_usage: true}}`. Requires `text/event-stream`, reads `choices[0].delta.content`, detects provider `error`, output truncation, and incomplete streams. Flutter's optional tool mode uses the additional function-call contract below. Images and the Responses API are not supported.

Model discovery adds `GET <baseUrl>/models` with the same optional bearer credential and URL/redirect policy. It reads `{data:[{id:string}]}` as documented by the [official models API](https://developers.openai.com/api/reference/resources/models/methods/list). The request has a 20-second total timeout, 1 MiB response cap and 512-entry cap; IDs are validated, deduplicated and sorted. There is no background fetching. The result does not guarantee each model supports text chat; unsupported/empty/malformed listings offer manual entry.

Flutter `listModels {baseUrl, apiKey?}` performs discovery against draft settings without saving them. `configure` optionally accepts `enabledModels` (1–32 IDs including `preferences.model`; defaults to that model). Bootstrap adds `enabledModels`. `selectModel {model}` switches to an enabled model, preserving the key, conversation and draft; active model and choices persist atomically with connection metadata. All are rejected during generation. Null/omitted keys reuse the active or remembered credential only for the same endpoint; explicit empty keys remain keyless. See [the full bridge contract](flutter/flutter-api.md).

Brick 2.2 adds Flutter `sessionsPage {cursor?,newer?}` (50 rows) and `messagesPage {session,cursor?,newer?}` (80 rows), each returning `{items,hasOlder,hasNewer}`. Bootstrap retains `sessions` and adds `sessionPage`; Flutter's initial list is now 50 rows. Keyset cursors exclude the boundary and preserve stable display ordering. The legacy `messages` call and provider context remain limited to 80 recent messages. `export {session,path,format}` streams a complete SQLite read snapshot into a new Markdown/JSON file and returns `{messageCount}`; absolute paths and matching `.md`/`.json` extensions are required, existing files are never replaced, and failed writes leave no partial destination. The UI uses the official [Flutter file selector](https://pub.dev/packages/file_selector) for the native Save dialog. All new commands are rejected during generation. See the scoped contract for export schema and ordering.

Brick 2.3.2 adds Flutter `context {session?,input}` for an on-demand, local-only request-context preview, `context` on started events, and optional completed-assistant `metadata {model,usage,context}` in history/export. Nullable token counts preserve missing versus zero and use only provider reports. Schema version 4 stores metadata atomically with its complete turn. Usage-only stream chunks are accepted; explicitly rejected usage options have one bounded pre-stream compatibility attempt. No automatic retries after transport/stream errors, token estimates or prices are added. See [the usage/context contract](flutter/flutter-api.md#usage-and-context-visibility) and machine-readable accounting types.

The context inspector adds `messages:[{role,content}]` to the `context` result: the exact bounded prepared sequence, including system instructions and the draft. Started events and saved metadata remain summaries. The trajectory inspector reuses independent `messagesPage` reads; its transient request lifecycle log is Flutter-only, bounded to 200 events, and never stores prompts, streamed chunks, credentials or network payloads.

Brick 2.4 adds Flutter `setRequestSettings {settings:{maxOutputTokens,timeoutSeconds}}` and nonsecret `requestSettings` in bootstrap. Integer bounds are 1–32768 output tokens and 1–900 seconds; defaults remain 2048/180. SQLite schema 5 persists settings independently of credentials. The OpenAI-compatible provider uses the saved output limit and one whole-response deadline, including its bounded usage-option compatibility attempt. Started events add nullable actual `requestSettings`; completed metadata optionally retains the same snapshot. Failure events add `recovery {kind,retryable,guidance}` for explicit user actions; no automatic failure retries. See [request controls and recovery](flutter/flutter-api.md#request-controls-and-recovery-brick-24).

Brick 3.1 adds optional `workspace` on Flutter `start`, optional `tools` on `context`, run-bound `approveTool {id,callId,allow}`, and `modelStep`, `toolApproval`, `toolResult` events. Tools are off without an explicitly selected absolute folder. Only the compiled `read_text_file` tool is registered; valid reads require a single-use user decision. The folder is not remembered, exported or sent to the provider. Successful assistant metadata optionally contains `agent {modelCalls,usageByCall,tools}`; file contents in those records are saved and exported with the reply. SQLite remains schema 5. See [the tool contract](flutter/flutter-api.md#approved-folder-tools-brick-31).

Tool requests use the same endpoint/authentication, `stream:false`, `tools:[{type:function,function:{name,description,parameters}}]`, `tool_choice:auto`, `parallel_tool_calls:false`, and configured `max_tokens`; no `stream_options`. An assistant `tool_calls` entry is followed by a `role:tool` message carrying its matching `tool_call_id`, only after local policy and approval. Require bounded JSON and a complete `stop` or `tool_calls` finish reason. No fallback or automatic retry for unsupported tools. Four model calls/four tools, 16-KiB results, bounded context and a whole-loop deadline including approval constrain the run; per-call usage is kept separately. Ordinary chat retains streaming.

Brick 3.2 registers `list_folder {path}` and `search_text {path,query}` alongside `read_text_file` in folder-enabled runs. Every operation requires a separate decision; `.` denotes the chosen root. Approval/result records add optional `query`, absent on legacy/read/listing records. Successful discovery status is `completed`; read status remains `read`. A denied operation is cached by tool, resolved target and exact query, without affecting another operation. Listing/search results are bounded JSON strings with root-relative paths, counts and truncation flags. Their persisted metadata/exports include names and matching snippets. No new network endpoint, ABI symbol, database migration, background indexing or write capability is added. See [discovery](flutter/flutter-api.md#folder-listing-and-text-search-brick-32).
