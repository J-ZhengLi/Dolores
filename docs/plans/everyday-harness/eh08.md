## Implementation design - October 24

Start runtime work after EH07.4 passes its regression gate. Own new core
history_search.rs contracts and SessionStore ports; SQLite history_search.rs,
history_search_tests.rs and additive schema 47; bridge history_search.rs,
command routing and tests; Flutter history_search.dart, sidebar entry and task
navigation, focused/rendered/native tests. Notification ownership follows in
EH08.2/EH08.3 with its own recorded native design before implementation.

Keep pin/archive state in a separate revisioned per-session record with a
cascading chat FK. An archive operation only changes organization: it cannot
clear a draft, consume input, cancel a goal or stop an active owner. Existing
recent pages omit archived chats; direct task navigation and active owners stay
available. A dedicated history inspector searches saved title/message text,
filters archive state, pin state and workspace, and opens exact task identities
through the existing AppHost navigation. Preserve legacy deletion semantics.

Use a rebuildable local SQLite full-text index maintained by transactional
triggers on canonical saved sessions/messages, including migration backfill.
Treat queries as literal text, never SQL or raw FTS operators. Qualify multilingual
and short-query behavior rather than assuming tokenization is sufficient.
Search result pages and snippets must be bounded; bind continuation cursors to
their query/filter/sort basis. Provide explicit rebuild with atomic rollback on
failure: history and prior results remain reachable and reads never send a
provider request. Pin/archive edits use optimistic revisions so another window
or stale inspector cannot overwrite a newer choice.

Verify migration/backfill, Unicode and punctuation queries, filters, ties/paging,
search after create/update/delete and failed/interrupted index rebuilds. Exercise
failed/stale organization edits with drafts, goals and queued input unchanged;
render compact Light/Dark search, archive restore and error/retry states. The
normal native bridge journey must search old message text, open the matching
conversation, archive it, find and restore it, and preserve an active task's owner.

### Search responsiveness and notification design notes - October 24

Use a one-second SQLite progress budget for synchronous history queries, based
on the public 1,000-turn indexed/short-query fixture completing in about 2 ms.
This keeps the command worker available for task control instead of admitting
unbounded short-text scans. Rebuild/backfill has 30 seconds. Host rebuild is
idle-only and holds admission through the operation; it refuses when a task is
owned, never cancels it, and permits explicit retry after completion. An aborted
transaction retains the previous index. Search takes no execution ownership.

For EH08.2/EH08.3, inspect exact run-journal event names before implementing
attention generation. Own core attention contracts, SQLite delivery/dedup and
preferences, bridge read/claim/resolve commands, AppHost attention routing,
Flutter attention/preferences UI and a Windows runner adapter. Reuse saved run
identity and event sequence. A notification carries only a generic status and
opaque local target; no prompts, paths, model output or task titles leave the
in-app view. Persist opt-in and delivery outcomes separately from task lifecycle.
Treat an uncertain native handoff as uncertain, without silently replaying it.

Use the existing Windows owner window for native notification callbacks; keep
notification identity separate from the scheduling tray icon. Honor quiet time
and unavailable delivery, preserve an in-app attention entry, and never present
API acceptance as proof that Windows displayed a notification. Resolve a click
against the current task/decision. Opening a notification only navigates; a stale
approval/question opens retained evidence and cannot answer or approve anything.
Keep failed/denied delivery recoverable through the same in-app decision path.

Windows API references for the adapter design:
[notification-area behavior](https://learn.microsoft.com/en-us/windows/win32/shell/notification-area),
[user notification state](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shqueryusernotificationstate),
and [notification data and quiet time](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataw).
Native callback routing, privacy, unavailable delivery, stale decisions, exact
task selection, deduplication and restart recovery need separate evidence;
saved Flutter renders alone do not qualify the Windows boundary.
