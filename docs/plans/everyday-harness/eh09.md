Archive contract limits: ZIP input 4 MiB; expanded files 2 MiB total; 512 KiB per
resource; existing SKILL.md 8 KiB; optional manifest 8 KiB; 64 files/128 entries;
relative UTF-8 forward-slash paths within 240 bytes and 12 components. An absent
manifest means schema 1, version `unversioned`, no declared origin/dependencies.
The manifest accepts only schema/version/origin/dependencies. Dependency entries
have name/requirement strings; no setup command or dependency execution is
admitted. File-byte hashes and a sorted, length-framed content hash bind resources
independently of ZIP entry order; a separate archive hash identifies exact input.

1. Package contract and archive inspection. Own new core skill-package contracts
   and bridge skill_packages.rs plus deterministic tests. Reuse the
   existing ZIP/SHA-256 dependencies. A package has root SKILL.md, relative
   scripts/references/assets and optional dolores-package.json metadata for its
   version, declared origin and dependencies. Inspection reads a bounded archive
   without publishing or executing anything. Distinguish publisher claims from
   the locally computed content digest; dependencies are displayed, not installed.
2. Reviewed installation and retained versions. Own bridge skill_packages.rs,
   scoped skill review integration, core SkillVersion/SkillSource optional
   package metadata and SQLite skill activation. Publish complete immutable
   content beneath an owned package directory before the atomic activation
   transaction. Bind review to scope, canonical destination, archive digest and
   saved revision. Failed publication or saving keeps the previous active
   version; a completed unreferenced publication remains inspectable for an
   explicit same-content retry. Rollback and export bind exact retained bytes.
3. User flow and resource context. Own Flutter skill_packages.dart and existing
   Skills inspector integration, package/context fixtures and acceptance docs.
   Review files, provenance, dependencies and version changes in a bounded
   scrolling inspector with fixed actions. Installation alone leaves tools and
   activation unchanged; activating requires its own explicit choice. Context
   exposes the selected package's immutable resource base and digest without
   embedding assets or executing scripts. Existing command/read permissions
   still apply. Render compact Light/Dark import, update and recovery states and
   exercise the connected normal-bridge resource/rollback journey.
4. Capacity recovery. Qualify the sixth distinct package update while five
   installed versions are also retained by saved activations. Current catalogue
   admission refuses a sixth entry and scoped removal refuses any saved-version
   reference; its offered direct recovery asks to forget the entire skill. Before
   closing EH09.1, provide an explicit reviewed way to release an older, noncurrent
   activation without clearing the current usable version. Keep the existing
   limits and removal guards; test failed save/stale review and successful retry
   through the sixth install/activation. Record the observed capacity refusal
   and concrete recovery evidence. This is a usability gap in the current
   capacity controls, not a reason to increase limits or evict silently.

Archive admission rejects absolute/escaping paths, Windows drive/UNC/alternate
streams and device names, links/special files, duplicate or case-colliding names,
file/directory collisions and malformed metadata. Bound compressed input,
expanded bytes, file count, per-file bytes and metadata before publication;
stream actual expanded bytes instead of trusting ZIP size fields. Test a normal
package with a script, reference and binary asset, escaping/colliding paths,
truncated or oversized input, and a failed update retaining usable old resources.
Record exact limits and any unsupported package format explicitly in the UI and
guide when implementing the archive contract.

For the next slice, keep installed package records separate from active skill
versions: Install must not implicitly enable or replace an active snapshot.
Use the locked profile's owned skill-packages directory (beside workspaces),
not the user's source collection or arbitrary project files. Pin a content
identity in each activated SkillVersion and carry it in SkillSource. Preserve
legacy records with absent package metadata. Package review/publication must
retain directory structure, including empty directories, and refuse destination
replacement; qualify this before using the archive inspector as an installer.
Keep bounded installed-version retention and explicit removal/recovery for
unreferenced publications. Do not silently accumulate or delete package trees.
Resource access must bind the frozen selected package and verify bytes; ordinary
folder and command permissions remain independent of installation/activation.

### Reviewed installation design - October 24

Own core skill_packages.rs/skills.rs and SessionStore ports, SQLite package
catalogue/schema 49 and skill activation, bridge package storage/commands and
tests. Retain installations in a separate scoped catalogue with at most five
versions per skill and twelve names per scope. Bound the profile's physical
cache to sixty bundles, including unreferenced publications. Refuse capacity
with explicit removal/recovery; do not evict files behind an active snapshot.

Publish bundles under the locked profile, keyed by exact archive SHA-256. Retain
the original ZIP, a host receipt and a payload directory; preserve empty folders.
Use capability directory handles and refuse links, aliases and replacement.
Installation publishes complete bytes before saving catalogue metadata; a failed
save leaves one identifiable bundle for same-archive retry. Installation does
not activate. Activation/rollback stores an optional immutable package snapshot
alongside the existing skill version, with optimistic revision checks and exact
retained package verification. Legacy versions keep absent package metadata.

Review tokens bind session, scope, canonical profile, exact archive and current
catalogue/skill revision. Export retains the original ZIP and refuses overwrite.
Explicit removal first drops only an unreferenced scoped registration; retain
the physical bundle when another scope or skill version references it. For an
unreferenced bundle, delete only verified owned files, preserving the source ZIP
and receipt until payload removal finishes. Failed/partial removal stays visible
as retained data for explicit retry; unknown or changed files refuse removal.
Lists and inspection never activate, grant tools, execute dependencies or replay
work. Qualification includes interrupted publication, failed catalogue writes,
stale reviews, scope/refusal guards, changed resources and safe removal recovery.

The backend also pins package archive identity in composer references and input
submission identity, including after a skill name is forgotten/re-added with the
same document and version numbers. The existing picker carries the full reference;
stale inspection cannot substitute a different package. Runtime source snapshots
retain package identity and resource base without embedding asset bytes in prompts.

Next UI/resource slice must exercise Project and Global installation through
rendered controls, package version/rollback and retained-data recovery, exact ZIP
export, and bounded verified resource reads in a normal model/tool request. Keep
the package task unchecked until these connected flows pass. In particular,
modified cache resources must retain an inspection/export route; no automatic
overwrite or speculative execution is approved by an import.
