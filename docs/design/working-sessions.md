# Brick 3.3 — Working sessions

The selected Flutter shell treats a working folder as conversation identity, replacing the launch-wide Folder tools toggle. Open project chooses and validates an existing folder, registers it in recent projects, and creates a new project chat. Sidebar New chat starts a temporary workspace, with Side chat in its menu. Project chats nest under their folder in collapsible Projects; a + action starts a new chat in that project. Temporary/side chats use Recents. Shared history paging stays visible below the grouped scroll area. Temporary chat creates a fresh app-managed folder on first send, without requiring a folder picker. Side chat explicitly has no folder or file tools and retains ordinary streaming. The header menu exposes all three modes and a Show working folder/Copy path dialog. Project groups and recent-chat mode labels stay visible in the sidebar; compact screens use the existing drawer. Selecting or creating a chat closes the drawer. Keep the system theme and composer footer order.

SQLite schema 6 adds `projects` and `session_workspaces` without rewriting messages or schema-5 tool metadata. Creating a conversation and its immutable folder binding is one transaction. Folder roots are canonical absolute local paths, stored only in the private application database and host UI responses. They are not automatically added to provider context or conversation exports. Old conversations have implicit Side mode. The host restores each chat's binding and opens its folder capability for each run; a request cannot redirect an existing chat to another folder or enable tools on a side chat. Missing/moved folders fail visibly rather than silently falling back to ordinary chat or a different root. Select another project to start a new chat.

Temporary folders live under the application data directory's `workspaces/<random session id>`. Each chat owns a different folder, persists across restart, and never inherits the last project's root. Temporary describes the workspace choice, not history deletion or automatic cleanup. Deleting a conversation cascades its association but never deletes working files. A failed database creation removes only a just-created empty temporary folder with nonrecursive removal. No scheduler or background cleanup is added. Working-session creation is local and does not require a connected provider; the default temporary folder is created lazily when sending, so startup/context inspection creates no empty records or folders.

Core exposes optional storage ports and typed workspace/project values; SQLite implements them, and the Flutter host owns directory validation/creation and tool registration. No additional dependency, sidecar, external plugin loader or filesystem authority is introduced. All existing per-operation approvals, exclusions, bounded scanning, cancellation, whole-run limits and durable result cards remain. Plain prompts in working sessions also advertise tools and use the agent protocol; streaming agent responses remain the next brick. The `workspace` argument to Start is retained for older direct clients only when creating a new project chat or confirming the same bound root; new Flutter callers send only the session ID. Start without a session creates a temporary working session.

Acceptance covers default tool availability and explicit approval, unique temporary folders, project recents, per-chat restoration and restart, legacy side mode, immutable scope, unavailable folders, pending-creation exclusion, atomic creation, export privacy and compact light/dark layouts. Native diagnostics exercise controller callbacks and real FFI/HTTP/SQLite, not OS pointer/keyboard/folder-picker UAT. Live-model, low-end and other-platform acceptance remain separate.
