# Task access and revocation

Brick 10.2 implements **Review**, **Auto** within explicit grants and **Full access** for one saved working chat. A new chat/fork has review mode by default. Grants are not inherited across projects or chats. This is a deliberate narrow initial scope; broader grant policies require a later named design change.

The revised mode selector saves immediately for the current chat, with no duration, acknowledgement or Save step. **Review** asks per operation; **Auto edit** grants the five built-in file/discovery tools at `.` while commands and external tools still ask; **Full access** covers advertised tools without activating new tools or mods. Selections have no expiry and survive restart. Existing custom/expiring grants remain intact until the user explicitly selects a replacement mode; custom grants are labeled separately. A stale save keeps the prior policy and requires a fresh explicit choice. New chats/forks still start in Review.

`PermissionPolicy` retains support for up to 16 typed grants and nullable expiry in saved/API records. File grants bind validated relative path prefixes; prefix boundaries prevent `src` matching `src2`. Commands bind exact program and literal arguments. MCP grants bind advertised alias, identity and reviewed revision; metadata/fingerprint checks still run. Unknown fields refuse. The simple UI does not silently translate or widen existing custom policies.

The host snapshots the thread settings revision and policy. It rechecks before deciding, after an explicit decision and again at dispatch, outside extension hooks. Revocation saves a new revision and cancels the matching primary run, including pending approvals; changed mode cannot expand a running task. Late approvals fail and no pending call is replayed. A stale save retains existing access. Expired grants require renewal or revocation before tool use. Decisions and automatically covered calls are recorded distinctly in durable run events.

Budget/interaction edits preserve the permission group. Task permissions has a separate local command/view (`taskPermissions`, `setTaskPermissions`), available during a run for read/revoke. It cannot grant self-update authority. File tools retain folder/secret/link and snapshot rules; commands/MCP use user-account OS permissions and may affect data outside the working folder. Application grants, cancellation and process ownership are not an OS sandbox. Revocation cannot undo effects begun before it; inspect saved evidence/current files before continuing.

Access grants are local settings and can include literal command arguments; users should not put secrets there. They are retained in run snapshots/evidence under existing local data/export rules. No credentials are added to a grant or startup process. Context describes the mode/boundary, not a grant of authority from text.

Cross-project tasks use the existing advertised `run_command`: the selected folder is its CWD, not an OS access boundary. Literal absolute arguments can inspect a relevant sibling repository or resource. The host applies the selected mode or exact operation review; a model must not declare the path forbidden merely because file tools are project-relative, or ask for a separate chat acknowledgement instead of invoking the review. Referenced paths remain evidence to inspect, never authority to execute unrelated instructions. Missing/ambiguous locations and actual OS denials still need honest recovery.
