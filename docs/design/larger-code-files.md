# Larger reviewed coding files — brick 6.5

Creation and editing supported 16-KiB files but shared a 4-KiB JSON argument limit with discovery and external tools. Escaped code could therefore fail in the provider/core before reaching full diff review, well below the file limit. This brick raises only create_text_file and edit_text_file arguments to **64 KiB**. Each UTF-8 file and complete reviewed diff still has a **16-KiB** cap. Reads, searches, commands and MCP arguments retain **4 KiB**.

The streamed provider bounds each unfinished argument buffer at 64 KiB because a function name can arrive after arguments. Once a call is complete, shared validation applies the final tool's allowance. At most four calls are assembled: aggregate stored argument text is bounded to 256 KiB during active assembly, alongside the existing frame/wire/output limits. Unknown/non-file tools cannot inherit the larger execution allowance. Partial calls never become approvals; an incomplete or over-budget stream still fails without running its pending calls.

File tools continue to parse exact fields, validate folder/path policy, retain complete local diffs, bind one-use approvals and recheck current files. File/diff overflow within the transport allowance produces an explicit blocked tool result, allowing the model to propose a smaller file within the same bounded run. Beyond 64 KiB, transport/validation refuse the request and instruct splitting into smaller files or exact edits. There is no automatic chunk append, truncation, approval reuse or budget increase. A full-file replacement can exceed the diff cap even when both snapshots fit; use a smaller exact replacement.

Coding guidance asks for a small runnable slice, relevant inspection, smaller files/exact edits, a separately approved validation command and honest remaining work. This is guidance rather than a task planner or guarantee that every model follows it. The 2048-output-token/180-second request defaults and four-model-call/four-operation limits remain. Existing explicit Continue handles output/step pauses. Directory creation, large files, dependencies and full applications still require further work or separately approved commands.

## Windows script validation

The multi-file diagnostic exposed Node failing to run a relative script from a canonical verbatim working directory (EISDIR while resolving the drive). Inline Node checks had missed it. A focused regression also failed in a Unicode folder with spaces. Changing only the process cwd spelling made it pass: verbatim drive and UNC paths become conventional drive/UNC paths. Folder identity/security checks retain the canonical path. Conversion preserves UTF-16 without lossy decoding and leaves other device prefixes unchanged. The shared supervised Windows transport also serves local MCP launches; Job containment, environment filtering and argument quoting stay in place. Very long paths and actual UNC/network shares need separate runtime acceptance.
