# Implemented run ownership

Brick 9.2 retains one active execution. A coordinator owns each client run ID's cancellation, approval slot and bounded UI queue. Wrong IDs cannot cancel or consume another run. Conflicting commands refuse; capabilities, run evidence, saved messages/workspace and Changes can be inspected locally during execution. The UI keeps foreground-chat switching locked until Stop/completion; safe cross-chat reads are exposed by the bridge, not a new concurrent-chat workflow.

Each primary chat execution receives a separate durable UUID before starting. Schema 20 adds `runs` and `run_events` without rewriting older tables. The snapshot freezes model, request settings, input, build and tool names. Approval and operation intent/result events use ordered sequence checks and an atomic snapshot/event transaction. Tool results retain bounded literal content, including command receipts. Streaming deltas remain transient; full durable task checkpoints/resume arrive in 10.4. Auxiliary skill/memory/comparison jobs retain their existing receipts and coordinator ownership; they are not represented as primary chat runs.

States are prepared, running, waitingForApproval, paused, completed, failed, cancelled and interrupted. Invalid/stale transitions refuse without partial writes. Ordinary evidence has 64 events, with a reserved terminal/restart marker; records are bounded to 128 KiB, histories display the latest 20 runs and a chat retains at most 100 runs. Exhaustion explains the allowance and offers a new chat. Recorded input/results are local private data, not automatically injected into context, exports or learning; deleting the chat cascades its run records.

The desktop host takes an operating-system file lock before opening/migrating the data directory. A second host refuses with close/restart guidance. The process holds ownership while its runtime may still have exiting jobs; Shutdown does not prematurely release it. At startup under that lock, unfinished primary runs become interrupted with an inspection message. An intent without a result is uncertain. No file/command/MCP operation is replayed. Existing file journals still describe file effects; external effects cannot be made exactly-once or undone by this log.

Failed evidence saves surface a warning alongside any saved reply; inspect Run history and Changes before retrying. Stop/deadlines retain the existing cancellation and bounded-delivery behavior. The file lock is process coordination, not an OS execution sandbox. Other platforms, physical native inspection interactions, full task checkpointing and richer history paging remain acceptance gaps.
