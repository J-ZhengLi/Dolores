# Brick 3.5 — Reviewed single-file edits

Brick 6.5 supersedes the former 4-KiB file-tool argument budget with 64 KiB; each file and complete reviewed diff still stays within 16 KiB. Other tools keep 4 KiB. See [larger coding files](larger-code-files.md).

Brick 3.6 adds independent local snapshots, durable intent and reviewed revert to the selected Flutter host; it supersedes this brick's lack of a durable journal. See [change journal](change-journal.md). The edit validation and optimistic concurrency limits below still apply.

Working project/temporary chats register `edit_text_file` alongside read/list/search. Its arguments are `{path,old_text,new_text}` with no extra fields. One exact, nonempty, unique match is replaced in an existing writable UTF-8 file. Overlapping/repeated matches, NUL/binary text, aliases and common credential/VCS paths fail preparation. The existing 4-KiB argument and 1024-byte relative-path limits apply; original/replacement files and the displayed diff each stay within 16 KiB. This brick does not create/delete/rename files or run commands.

Preparation reads a bounded local snapshot and holds its parent directory capability. It produces a unified diff with real line numbers, three context lines and explicit missing-newline markers. This local preview is shown before writing; no model text or tool argument grants permission. Each prepared plan is keyed by call ID, bounded by the four-tool run budget and consumed once. Approval binds name, target and the exact preview. Denials include the diff in their identity, so a different proposal requires a separate decision.

After Apply once, the worker revalidates the direct path, bytes and ordinary permissions. It stages the replacement with exclusive creation beside the target, copies ordinary permissions, flushes it, then repeats the checks and observes Stop immediately before atomic rename. Failed staging/publication cleans only its own temporary file; the original remains intact. Temporary edit names are excluded from all folder tools. Directory handles prevent Windows parent renames while held. Atomic replacement does not modify the contents of other hard-link names.

Changed-file checks are optimistic, not a cross-program compare-and-swap guarantee: another process can still modify a file between the last check and rename. Do not claim protection against every concurrent external writer. Atomic replacement preserves ordinary permissions, not every platform ACL, extended attribute, timestamp or hard-link relationship. macOS/Linux behavior remains unverified. A process crash can leave a staged file; there is no automatic cleanup of unknown files.

Cancellation is checked before publication; an OS rename already begun cannot be interrupted. Applied edits are filesystem effects and remain if a later model request, Stop, timeout or conversation save fails. The approval card states this. Existing complete-pair history rules remain: final text and optional tool metadata commit together only on success. Failed-run records are transient, not a durable edit journal or rollback mechanism.

`ToolRequest.diff` and `ToolRecord.diff` are optional, preserving old records and schema 6. Successful edits have status `edited` and JSON content `{applied:true,bytesBefore,bytesAfter}`; conflicts return a fixed explanation without overwriting. Chat/trajectory share selectable literal diff rendering with removed/added lines using existing semantic colors. Large line counts fall back to uncolored complete text. Diffs are retained unencrypted in successful metadata and full exports; only the short edit result returns to the model during that call.

Rejected argument shape, missing/ambiguous matches and size-limit errors return specific allowlisted local feedback, never raw arguments/paths or plugin errors. A corrected proposal still needs a new local preview and single-use approval. This permits bounded model recovery without weakening the policy.

Acceptance covers no mutation before approval, Deny/Stop, exact Unicode/CRLF changes, ambiguous matches, changed snapshots, path redirection, single use, failed publication cleanup, saved/reloaded/exported diffs and one synthetic live-model edit. OS input, multi-file transactions, undo/rollback, broad patching and shell access remain separate bricks.
