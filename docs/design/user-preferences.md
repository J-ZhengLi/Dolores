# Reviewed preferences — brick 4.1

Current behavior adds [automatic preferences](automatic-memory.md), enabled after saved replies. The manual workflow below remains available when learning is disabled.


Memory is now available under the single sidebar Settings entry in working and Side chats, using the shared settings editor and theme. Users explicitly write short preference entries, choose All chats or This working folder, and decide whether to use each entry in new messages. Show exact text, Added by you, scope, enabled state and modification time. Save is the explicit review/activation step; Close/Cancel never save. Edit, disable/re-enable and delete remain available without a model call. There is no automatic extraction, file import, model-written memory, embedding index, watcher or background worker.

Keep at most 12 entries per scope, 80-character titles and 1024 UTF-8 bytes per preference. Store entries in additive SQLite schema 11, with a random ID, integer revision, creation/modification times and source=user. Resolve a folder scope only from the saved session; never accept a client-supplied root or expose it in exported metadata/provider context. Side and uncreated temporary chats use only All chats preferences. Entries survive deleting a chat; they are controlled separately in Memory.

Use optimistic revisions for edits, toggles and deletion. A stale view or failed transaction cannot overwrite newer entries or discard the form. Scope is fixed on editing; create a separate entry to change scope. Reject invalid text/IDs/scopes and creation past the per-scope cap. Do not create secrets from prompts or tools; saving/sharing entered text is explicit. Memory is local plaintext application data, so ask users to keep credentials out of preferences. Deletion stops future retrieval and removes the active record; historical replies and provenance remain. No forensic erasure guarantee is claimed.

Select complete enabled entries deterministically: current folder first, then All chats, newest modification first with a stable ID tie-break. The serialized entry text has a combined 4096-byte budget; skip entries that cannot fit without truncating them, and report used/omitted enabled entries honestly. Shared preview/send preparation appends literal preference text to the system message, counts it in existing byte/token budgets, and preserves whole newest history turns. Direct user requests, reviewed workspace guidance and host policy take precedence; folder preferences outrank All chats preferences. Preferences cannot approve tools, run code or load referenced paths.

Context preview shows exact used entries and source/revision/scope, including omitted counts. Completed metadata retains a compact provenance snapshot without duplicating preference text. Editing/disabling/deleting affects subsequent requests; a running request retains its initial snapshot. Past exported replies can mention a preference, and their retained provenance is not silently rewritten. Add a manual Memory recovery action for malformed storage/preferences.

Verify isolated manual creation/correction, disabled/deleted exclusion, folder/Side isolation, deterministic bounded selection, stale-save/delete refusal, atomic rollback, startup migration, restart/export, exact provider input versus preview, unchanged tool approval and compact light/dark UI. Frozen mock checks establish retrieval behavior, while live Qwen probes report their actual instruction-following outcome. Native callback/renderer checks do not replace OS input/accessibility or low-end/platform acceptance.
