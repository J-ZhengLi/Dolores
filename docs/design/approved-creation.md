# Reviewed new files — brick 3.7

Brick 6.5 supersedes the former 4-KiB file-tool argument budget with 64 KiB; each file and complete reviewed diff still stays within 16 KiB. Other tools keep 4 KiB. See [larger coding files](larger-code-files.md).

Project and temporary chats can propose `create_text_file {path,content}`. This makes an empty working folder useful without enabling a shell. The path is direct and relative, its parent must already exist, and content is complete literal UTF-8 text. All fields are required; unknown fields are rejected. Existing files, directories and aliases are refused. Traversal, device, secret/VCS and internal staging paths use the same policy as edits. No directory-creation or arbitrary-deletion tool is added.

The existing 4-KiB serialized argument budget includes path, content and JSON escaping. File text and the complete addition diff have separate 16-KiB caps; the smaller argument budget normally controls creation size. Empty files are supported. Unicode, CRLF and missing final newlines are preserved exactly as proposed. The model can still propose the wrong content: the local review is authoritative, and no formatter silently repairs it.

## Review and publication

Preparation checks the path and absence, then saves a call-bound plan without writing or sending a local snapshot to the model. The card displays a literal complete addition, `/dev/null` before-header and missing-newline markers, with Create once and Deny. Tampering with its name, target, query or diff consumes and refuses the plan. Deny and Stop never invoke it. The bounded registry and denial cache retain the existing four-call limits.

Publication exclusively stages the content beside the destination, flushes it, and saves a FULL-synchronous journal intent. It checks cancellation, the direct parent and absence again, then creates a hard link from the owned staging file to the new destination. The link operation never replaces an occupied entry, including one appearing after the last check. Cleanup removes only the owned staging name. A filesystem without hard-link support fails safely; there is no rename or overwrite fallback. Windows NTFS was exercised; macOS/Linux and other filesystems remain unverified.

Intent failure prevents publication. A publication failure attempts a notApplied receipt. A successful publication remains successful even if its receipt fails: result content includes `applied:true,created:true,bytesBefore:0,bytesAfter,changeId,journalStatus:applied|pending`, and record status is created. The applied file and independent journal remain after Stop, model failure, failed conversation saving or deleted chats. Existing unjournaled alternate registrations omit changeId/journalStatus; the selected Flutter host uses the journal.

## Existence and reviewed removal

SQLite schema 8 adds explicit before_exists/after_exists booleans. Schema-7 replacements migrate with both true and unchanged snapshots. An absent snapshot has empty text plus a false existence flag; an existing empty file has empty text plus true. Neither byte counts nor empty text imply absence. FileChange summaries expose beforeExists/afterExists, and Changes labels Created, Edited and Removed separately from receipt status. Raw snapshots and private roots stay outside automatic context and conversation exports.

Review revert for an original pending/applied creation prepares a local removal only when its current file matches the saved created bytes. The existing root/session/change-bound, five-minute, one-use token now carries an operation of restore or remove. A removal shows the complete deletion and Remove once, with Cancel. It is available only through Changes; no deletion tool is advertised to the model. Empty files use the same explicit existence checks.

Removal rechecks direct path, exact text and ordinary permissions before saving its reverse intent and again afterward. It removes one regular file through the held directory capability and records its own receipt plus the original's reverted status atomically in SQLite. An intent failure prevents removal; a receipt failure still reports actual removal with pending status. Changed, missing, binary, read-only or alias targets are refused. Cancel/Close, stale tokens, another session, repeat decisions and active generation cannot remove the file. A removal cannot itself be reversed here; its saved snapshot remains inspectable. No directory or unknown file is removed.

These removal checks are optimistic, not an atomic compare-and-swap against another program. A concurrent writer after the last check can race removal, as with existing replacement/revert checks. Hard-link publication's refusal to overwrite is stronger than that separate removal boundary. Ordinary permissions are checked; universal ACL/xattr/timestamp/hard-link preservation is not claimed. Neither filesystem publication nor removal is transactional with SQLite. Crash cleanup, reconciliation and disk retention remain manual; no idle work, dependency or background worker is added.
