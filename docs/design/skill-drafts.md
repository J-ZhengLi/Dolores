# Reviewed skill drafts — brick 5.2

In a saved chat, open **Skills**, choose Project or Global, then **Draft from chat**. Select 1–3 completed exchanges you consider useful, review their complete text, and explicitly Generate. The latest 20 exchanges are offered; selected request/response text is bounded to 16 KiB. This selection records the user's judgment, not an automatic claim that work succeeded. Generating sends both sides, including any tool output quoted in the assistant response, to the configured provider. Nothing is sent during local review.

Generation uses one tool-free request with the model's saved output-token and timeout settings. The source review exposes Draft output tokens (1–32,768) and Draft timeout (1–900 seconds); edits override this generation only, without changing saved settings or evaluation limits. The request is frozen and checked against the configured context window before transport. There is no hidden 1024-token or 30-second drafting cap. The full request deadline and UI wait use the chosen timeout, with ten seconds of UI scheduling allowance. The 8 KiB response/document limit remains independent of the token allowance. Some models share their output allowance with reasoning, as illustrated by [Qwen's thinking-budget implementation](https://github.com/QwenLM/Qwen3/blob/main/docs/source/getting_started/thinking_budget.md); larger allowances can increase usage and are never selected automatically.

It receives only selected exchanges and a drafting instruction; no additional history, memories, folder instructions, skills or tool schemas. The prompt asks for a narrow workflow within 300 words, a short trigger description and one exact response quote inside an evidence array, leaving room to complete the JSON. An explicit JSON shape is serialized from the same SkillDraft type used by the parser; fixed placeholder text keeps untrusted exchanges out of system instructions. Validation still accepts 1–3 bounded quotes. Syntax failures are labeled invalid JSON; valid JSON with the wrong field/types is labeled a required-format mismatch. Typed parsing uses the original text, so duplicate and unknown fields remain refused; errors do not echo provider text. Invalid/mismatched quotes, credential-like content and oversized proposals are refused. Bounded metadata needing correction (such as an underscore in a name) opens in the editor with a validation notice; it cannot be tested or saved as a skill until corrected. Output-limit failure identifies the actual token allowance and suggests increasing Draft output tokens or selecting less source text. Selections and review token remain available for explicit retry; truncated JSON is discarded. No automatic retry or repair request occurs. Users can edit the three instruction fields before testing; the evidence remains bound to the selected exchanges.

The saved document uses the [Agent Skills specification](https://agentskills.io/specification): quoted YAML `name`/`description`, followed by literal Markdown. Existing ASCII naming and 8-KiB document bounds apply. Generated skills use the same project/global activation limits, precedence, context preparation and version store as imported files. No script, include or reference is executed. No source file is written by drafting, testing or promotion; reviewed documents and evaluation receipts live in local SQLite. Context provenance labels these as Dolores reviewed drafts instead of suggesting a source file exists. Reviewing a saved generated version shows its origin and receipt instead of presenting a missing file as an error. If an independent same-name file exists, it remains separately reviewable.

## Frozen response comparison

Define 1–3 response tests. Each has a prompt up to 2 KiB, 1–4 required exact snippets and 0–4 forbidden snippets (128 UTF-8 bytes each). Snippets are case-sensitive; the editor uses one per line. Empty, credential-like and contradictory tests are refused. A nonempty response passes only if it contains all required and none of the forbidden snippets.

Before the first request, the host freezes and checks both prompt sets against the configured model window and existing byte/token allowance. Baseline uses the ordinary host instruction and current effective saved skills. Candidate uses the same setup, with the edited draft replacing the same-name entry in the selected scope. Other skills remain identical. Each prompt is a fresh response test: conversation history, memories, AGENTS.md and tool schemas are excluded. A global draft overridden by an enabled project entry is refused here; test it in a side chat or another folder. All candidate skill limits are checked before transport.

Requests run sequentially, baseline then candidate per test, using one frozen provider/model/settings snapshot. Each is capped at 512 output tokens and 10 seconds (or lower configured limits): at most six requests, no tools or automatic retry. Progress identifies the test and phase, with Stop available. Outputs are additionally bounded to 8 KiB each. All tests must complete to publish a result. The app does not add a temperature parameter that some providers reject, so repeated scores may vary with model sampling; the captured requests and outputs describe this single run.

**Promotion requires every candidate test to pass and strictly more candidate passes than baseline passes.** A tie, failure, partial result, Stop, timeout or invalid response cannot promote a skill. The UI displays both responses and checks; activation remains a separate explicit action. These literal response tests do not evaluate tools, task completion, hidden reasoning, robustness, general skill quality or representative hardware. They are a bounded evaluation foundation, not proof of universal outcome improvement. Users can write weak checks; review the full responses and use held-out prompts rather than copying the drafting examples.

## Review and persistence

A five-minute in-memory token binds session/scope/folder, selected exact exchanges and generated evidence. Successful generation and evaluation issue fresh tokens. Edits disable the UI's promotion action; evaluation immediately clears any prior passing result before its requests begin. The host only promotes its exact tested document, never new caller-supplied text or scores. All commands use the existing active-run exclusion. Matching-token discard prevents an old dialog from clearing a newer review; cancelled/replaced workers cannot publish late results.

After evaluation, and again inside the promotion transaction, the host rechecks selected user/assistant pairs, working-folder association and the entire saved project/global collection. Concurrent skill changes require another evaluation. Promotion atomically compares revisions, applies limits and appends one version with its receipt. Failed writes retain previous state and allow explicit retry while the review remains fresh. Legacy side chats without workspace rows are treated as side chats; a missing/deleted source is still refused.

Receipts retain exact baseline/candidate system and user messages, expected snippets, responses, provider-reported usage where available, generation/evaluation model IDs, evaluation settings, configured window, time and baseline version provenance. Credentials and provider URLs are excluded. They are local plaintext and may contain reviewed skill text/source quotes. Receipts are bounded by three tests, 24 KiB per prompt set, 8 KiB per output and the existing five recent versions / 12 entries per scope. Retention, Forget and Disable remain explicit. Rollback preserves the old evaluation as a historical receipt; it does not re-test the version against today's model or context. Only instruction text enters future model requests, not evaluation responses or checks. Existing reply metadata/exports retain skill provenance; standalone skill/receipt export is future work.

SQLite schema remains 14 with an optional evaluation field in existing version JSON. Legacy versions omit the field without rewriting data. No dependency, process, background watcher or model worker is introduced while idle. The Flutter flow uses InspectorFrame, system-theme tokens, a scrolling body and fixed wrapping actions. Pending requests lock edits/closing/duplicates while retaining Stop; Close discards local draft state without activation.

Verification combines Rust validation/atomic storage/token tests, compact light/dark Flutter interaction tests, native release UI/FFI/HTTP/SQLite checks, and separate-process frozen-provider receipt/rollback checks. Live provider probes are recorded separately and cannot establish universal model adherence or platform/input/resource acceptance.
