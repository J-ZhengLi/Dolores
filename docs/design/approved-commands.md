# Approved commands — brick 3.8

This brick adds a separate compiled command plugin to working chats. `run_command {program,args}` runs one installed development executable with literal arguments and the saved working folder as its current directory. It uses no shell expansion or command concatenation. Initial program IDs are git, node, python, python3, cargo, rustc and dart; only direct installed executables resolved from absolute PATH entries outside the project are accepted. Windows batch scripts are unavailable. Arguments are required, at most 32, and the complete JSON is limited to 4 KiB.

The approval shows the selected executable's absolute path locally, the program and each argument separately, and the working folder. Run once/Deny is specific to that exact proposal; changing an argument or executable requires a fresh review. A directory is not a sandbox. The command has user-account permissions, may access/change files outside the working folder and use the network. Interpreter arguments and project build hooks may execute project code. There is no elevation or blanket permission. Command file effects are not covered by Changes, cannot be rolled back automatically and remain after Stop or failed conversation saving. Output is shared with the selected model and retained/exported with a completed reply.

Child environment is rebuilt from a small platform/runtime allowlist; arbitrary inherited API-key/token variables are excluded, but executables can still read user files and credentials with normal user permissions. Input is closed, terminal prompts/colors are discouraged, no visible console is created on Windows. Executable metadata is checked again after approval. PATH resolution skips relative entries and project-owned directories; this is a selection guard, not protection against concurrent replacement of system executables.

One invocation has a 30-second deadline and an 8-KiB combined raw stdout/stderr capture cap; exceeding the cap stops the process. JSON output is further shortened if escaping would exceed the existing 16-KiB result budget, with explicit truncation and lossy-UTF-8 indicators. A read failure or incomplete 200-ms drain marks outputError and truncated rather than claiming complete output. Nonzero exits preserve their code and output. The existing four-model/four-tool-call and whole-agent limits remain. No command runs before approval, on Deny or on Stop at approval.

Windows creates a hidden suspended process, binds it to a kill-on-close Job object, then resumes it. Failure to establish the job refuses execution. Only the three standard pipe handles are inherited. Job cleanup runs on completion, timeout, output limit, cancellation and dropped async invocations. Unix uses a new process group and kills that group on cleanup; deliberately detached or externally launched processes are outside that guarantee. Commands are not security-isolated on either platform. Platform checks and acceptance are recorded separately; Windows is the local validation target.

Windows implementation follows Microsoft's [process creation](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-processes), [Job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [process flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) and [explicit handle inheritance](https://learn.microsoft.com/en-us/windows/win32/procthread/inheritance) contracts. The plugin owns active process/pipe handles and bounded reader workers only during invocation; no service, shell sidecar or idle polling is added. Arbitrary command CPU/memory use is not capped and must not be included in claims about harness idle performance.
